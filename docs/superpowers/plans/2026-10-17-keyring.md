# Keyring Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new `ITEM_KEYRING` object type that holds only keys, counts for lock/unlock,
and can be used (look in / put / get) while hung on a belt hook.

**Architecture:** Two `obj_data` predicates (`is_keyring()`, `holds_items()`) are the shared
"container or keyring" test. `has_key()` (the single lock/unlock key lookup) learns to search
keyrings. One finder, `find_belt_keyring()`, gives `put`/`get`/`look in`/`examine` a proper
keyword lookup of belt-worn keyrings before their normal search. Every other site keeps
today's code, with the keyring added only where the spec says "normal rules".

**Tech Stack:** C++ (32-bit server), GTest `ageland_tests` via `scripts/rots-docker.sh test`.

**Spec:** `docs/superpowers/specs/2026-10-17-keyring-design.md`

## Global Constraints

- `ITEM_KEYRING` = **26** (`structs.h`, after `ITEM_LEVER 25`). Type name `"KEYRING"` /
  `"keyring"`.
- Keyring values: `value[0]` = capacity in weight units **including its own weight** (same
  check as a bag, `perform_put`, `act_obj1.cpp:39`). `value[1..4]` unused and **never read**
  — a keyring is never closed whatever `value[1]` holds.
- Only `ITEM_KEY` objects go on a keyring.
- **No behavior change for bags/containers/quivers/corpses**, including held bags.
- Held keyring: counts for lock/unlock; `put`/`get` don't reach it; `look in`/`examine` keep
  today's crude equipment match (no new code for held).
- Keyrings inside another container are **not** searched for keys.
- Worn-weight drift (`worn_weight`/`encumb_weight`) is a known, deferred issue: **don't fix it,
  don't assert those two fields in tests.** Carried weight (`IS_CARRYING_W`) is asserted.
- Player messages ≤ 78 columns, end with `\n\r`, game's own wording style.
- Format only changed files: `cd src && clang-format -i -style=WebKit <files>`. Never `make format`.
- After touching `structs.h`, rebuild clean (`make clean` / fresh cmake build) — header deps are
  unreliable.
- Commits: local only, never push. End messages with
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` (no other trailer).

## Exact player-facing text (my calls, pinned)

| When | Text |
|------|------|
| put a non-key on a keyring | `Only keys can go on a keyring.` (mirrors `Only arrows can go into a quiver.`) |
| `put all <keyring>` with no keys carried | `You don't seem to have any keys to put on it.` |
| open / close a keyring | `A keyring is always open.` |
| lock / unlock / pick a keyring | `A keyring has no lock.` |
| look in a belt keyring (header) | `<first keyword> (worn) : ` then the normal contents list |

## Review Focus

1. **Belt keyring vs. another worn item with a similar name** (e.g. a "ring" on a finger) —
   `put key ring` must reach the keyring on the belt, never the finger ring. Test in Task 3.
2. **Keyring with a stray `value[1]` CONT_CLOSED bit** from a builder copying bag values —
   must still accept put/get/look in. Tests in Tasks 3 and 4.
3. **`put all keyring` with mixed inventory** — keys go on, other items are left alone, no early
   stop like the quiver loop. Test in Task 3.
4. **Breakable key on a keyring** — breaks once, stays on the ring, further unlocks fail. Test in
   Task 2.
5. **Character dies with a keyring in a bag** — the keyring (with keys) ends up at the corpse
   top level, not hidden in the bag. Test in Task 6.
